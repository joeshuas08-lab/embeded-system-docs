# 开发者中心助手（更聪明）调教规范文档

更新时间：2026-04-14
基线提交：8d0020e
适用对象：后续需要重新训练、重建、复刻、迁移或恢复“开发者中心助理”能力的人或系统

一、目标定义

目标不是做一个“会说话的大模型前端”，而是做一个面向 SoC / 核心板 / BSP / 接口 / 驱动 / 选型 / 排障场景的检索增强技术问答代理。

调教目标必须同时满足：
- 聪明：先判断问题类型，再决定找什么资料
- 专业：结论必须和证据严格对应
- 迅速：尽量减少无效检索和无效 token 消耗
- 稳定：换问题、换模型、换上下文长度后结果尽量不漂

如果只优化其中一个维度，例如只换更强模型、不做检索治理，最终都会退化回“会说但不稳”的状态。

二、总体架构原则

正确架构不是：
- 用户提问 -> 把全量资料丢给模型 -> 模型自己挑 -> 输出答案

正确架构应是：
- 用户提问
- 问题分类
- 品牌 / 产品识别
- 候选资料召回
- 文档类型识别与加权
- 证据适配体检
- 对比题双边取证
- 将少量高质量资料交给模型总结
- 输出结构化工程师答案

一句话原则：
先让程序决定“哪些资料有资格回答这个问题”，再让模型决定“如何把这些资料讲清楚”。

三、产品识别原则

1. 目录优先于文件名

产品识别优先使用目录结构：
- `downloads/<品牌>/<产品>/...`

约定：
- 一级目录 = 品牌
- 二级目录 = 产品

原因：
- 文件名可能是共用命名
- 文件名可能带历史遗留命名
- 文件名可能按平台族合并命名
- 目录才是真正的资料归属

例如：
- `downloads/Allwinner/MYD-YT113S3/...`
- `downloads/Allwinner/MYD-YT113i/...`

即使文件名都叫：
- `MYC-YT113X Product Manual-V1.1.pdf`

也必须优先认目录归属，而不是只看文件名中的 `YT113X`。

2. 产品 token 识别应包含四层

产品 token 应至少由以下四层构成：
- 目录产品名原文，例如 `myd-yt113s3`
- 目录产品名拆词，例如 `yt113s3`
- 紧凑写法，例如 `mydyt113s3`
- 别名扩展，例如 `t113s3`, `t113i`, `t113x`, `yt113x`

3. 必须支持型号别名扩展

典型场景：
- `t113` 需要扩展到 `t113s3`、`t113i`、`t113x`、`yt113x`
- `j7a100t` 需要扩展到 `j7`、`tda4`、`a100t`
- `st257`、`ld257`、`lt257` 应互相补齐

原因：
- 文档命名、用户提问、产品宣传口径经常不一致

四、问题分类规范

所有问题必须先分类，至少分为：
- `doc-discovery`：文档发现类
- `intro`：产品介绍 / 参数 / 规格类
- `compare`：差异对比类
- `troubleshooting`：适配 / 排障类
- `general`：兜底类

分类意义：
- 不同问题需要不同文档类型
- 不同问题需要不同排序权重
- 不同问题需要不同回答约束

典型例子：
- “有哪些 LVDS 文档” -> `doc-discovery`
- “T527 的主频” -> `intro`
- “T113S3 和 T113i 的区别” -> `compare`
- “RK3576 如何适配新的 LVDS 屏” -> `troubleshooting`

五、检索来源规范

至少包含以下三类来源：

1. 文件级索引
作用：广召回，先知道有哪些候选文件

2. 章节级索引
作用：精召回，知道文件内哪些章节真正相关

3. 本地 references / memory / 其他沉淀文件
作用：补充工程经验、平台知识、历史结论

推荐策略：
- 文件级用于广覆盖
- 章节级用于提高相关性
- 两层结果合并后统一排序、去重

六、文档类型体系

每份候选资料必须识别 docType。推荐最少支持：
- `product-manual`
- `pin-list`
- `hardware-design-guide`
- `hardware-user-guide`
- `guide`
- `sch-pcb`
- `silkscreen`
- `3d`
- `benchmark`
- `generic`

推荐做法：
- 短期：根据路径、文件名、章节标题、摘要推断 docType
- 长期：在索引构建阶段直接生成 docType 字段，避免运行时猜测

七、按问题类型加权的规则

1. `intro` / `compare`
强升权：
- `product-manual`
- `pin-list`
- `hardware-design-guide`
- `hardware-user-guide`

强降权：
- `silkscreen`
- `sch-pcb`
- `3d`
- `benchmark`

原因：
- 介绍和对比问题的本质是“规格、平台能力、型号差异”
- 只有规格类文档有资格支撑这类结论

2. `troubleshooting`
优先：
- `guide`
- `hardware-design-guide`
- `hardware-user-guide`
- `sch-pcb`

中等：
- `product-manual`
- `pin-list`

弱化：
- `silkscreen`
- `3d`

原因：
- 排障看重链路、时序、配置、接口细节，不是先看营销式参数页

3. `doc-discovery`
策略：
- topic-first
- 放宽型号约束
- 允许按主题词命中文件名、章节名

原因：
- 文档发现类问题的目标是“找到对的资料”，不是“严格回答参数”

八、证据适配体检

所有回答前，必须先做 evidence fit 检查。

推荐分级：
- `good`：命中了适合当前问题的核心资料
- `weak`：命中了部分相关资料，但证据仍偏弱
- `mismatch`：命中了资料，但资料类型不适合当前问题
- `none`：无命中

应用规则：
- `good`：允许给出正常专业结论
- `weak`：只能保守回答，不能输出过强确定性
- `mismatch`：禁止硬答，必须明确指出资料类型不适配
- `none`：只能基于通用经验，且必须写明边界

典型 mismatch 场景：
- 用 `3D` 图回答主频
- 用 `benchmark` 回答规格差异
- 用 `silkscreen` / `SCH&PCB` 回答 SoC 对比

九、对比题双边取证规范

这是非常关键的一条。

如果问题类型为 `compare`，并且识别出两个产品目录，则必须强制：
- 从 A 产品目录取至少 1 份核心资料
- 从 B 产品目录取至少 1 份核心资料

推荐优先级：
1. `product-manual`
2. `pin-list`
3. `hardware-design-guide`
4. `hardware-user-guide`

原因：
- 单边资料只能证明平台共性
- 双边资料才能证明差异

例如：
- `MYD-YT113S3`
- `MYD-YT113i`

必须尽量同时拿到两边的 Product Manual / Pin List，不能只拿 `YT113S3` 一边后就让模型自由发挥。

十、模型输入规范

不要只把“问题 + 命中文档”丢给模型。

传给模型的内容建议至少包括：
- 用户问题
- 问题类型
- 证据适配状态
- 检索命中文档
- 每份文档的 docType
- 若 evidence fit 为 `weak` / `mismatch`，显式告诉模型不要硬答

原因：
- 模型不是天然知道这份资料有没有资格回答当前问题
- 必须把检索层判断同步给它

十一、回答模板规范

建议统一为：
- 结论
- 关键依据
- 主因断言 / 失败主因 Top3
- 落地建议
- 最小补充信息清单（必要时）
- Sources

硬约束：
- 结论先行
- 默认中文
- 工程师口吻
- 电报式短句
- 不写营销话术
- 不使用大段空泛铺垫
- 不在证据不足时装作确定

十二、反幻觉硬规则

以下规则必须硬编码到系统或技能约束中：

1. 参数类问题没有可靠规格资料时，不给确定参数
包括但不限于：
- 主频
- DDR 容量
- 温度等级
- 接口数量
- 支持列表

2. 资料类型不匹配时，禁止硬答
例如：
- benchmark -> 不能直接回答规格
- silkscreen -> 不能直接回答芯片差异
- 3D -> 不能直接回答主频

3. 对比题没有双边资料时，不下逐项差异结论
可以说明：
- 当前能确认平台共性
- 当前不能确认芯片级逐项差异

4. Sources 必须能支撑结论
不是只要列了 Sources 就算专业。
必须确认：
- 这些 Sources 真的有资格支撑当前问题

十三、适配题专门规则

针对接口 / 外设 / bring-up 类问题，不能只返回产品手册。
必须优先混入专题文档，例如：
- LVDS
- MIPI DSI
- MIPI CSI
- USB PHY
- RGB
- eDP
- Ethernet PHY

原因：
- 产品手册说明“有什么”
- 专题开发指南说明“怎么配、怎么调、怎么验证”

十四、性能与稳定性原则

1. 程序做粗筛，模型做精筛
- 不要把全量资料直接喂给模型
- 这样会导致 token 爆炸、速度下降、噪声增多、结果漂移

2. 响应默认短答
建议：
- 关键依据最多 4 条
- 下一步建议最多 3 条
- 只有用户要求时才展开长文

3. 输出后处理必须稳定
包括：
- Sources 统一格式
- 不暴露路径和 `.md`
- 拦截提示词泄露
- 证据等级规范化

十五、这套调教成功的关键能力清单

如果以后要重建同等级助理，以下能力缺一不可：

1. 品牌 / 产品目录索引
2. 型号别名扩展
3. 问题分类器
4. 文件级 + 章节级双层检索
5. 文档类型识别
6. 按问题类型的文档加权
7. 证据适配体检
8. 对比题双边取证
9. 技能侧的工程师回答规范
10. 参数类问题的反幻觉守门
11. Sources 规范化输出
12. 提示词泄露拦截

如果少掉其中任意 2~3 项，系统通常会退化为：
- 搜得到，但挑不准
- 说得顺，但证据脏
- 看起来专业，实际不稳

十六、当前已验证过的关键改进点

已验证有效的改进方向包括：
- 文档发现类问题走 topic-first
- 技术适配类问题强制保留接口专题文档
- T113 系列产品别名扩展
- 目录优先识别产品归属
- 对比题双边平衡取证
- 证据类型不匹配时禁止硬答
- 回答风格改成资深 FAE 式短句与断言

十八、最后的原则

不要追求“像人一样会说”，要追求“像资深 FAE 一样，先拿对证据，再给对结论”。

这套系统真正的专业，不来自花哨措辞，而来自三件事：
- 先找对资料
- 再判定这些资料能回答到什么程度
- 最后只在证据允许的边界内输出结论
